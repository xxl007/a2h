# ADR 0003: Design foundations: base library and visual role model

- Status: proposed (awaiting product-owner approval)
- Date: 2026-10-21
- Deciders: product owner (Galem L.), PM agent, Design agent
- Scope: the component base for `packages/ui` and `apps/web`, the colour role model, the neutral, typography sourcing, and the guest rules for the MCP App card. Governs the rewrite of `.claude/skills/a2h-design` §2–§3 and every `design.md` from M2 on.
- Related: `docs/design/survey-implementation-systems.md`, `docs/design/survey-design-languages.md`, `docs/design/foundations-brainstorm.md` (audit of the prototypes; its three invented directions were rejected by the owner), PRD §6.4, §6.6, §7, §11; CLAUDE.md accessibility and provider-neutrality rules.

## Context

The click-through prototypes carry the product decisions for M2–M5 but their visual foundations were chosen quickly: three web fonts totalling 269 KB against a 2 s budget on 3G, four light-mode text pairs failing WCAG contrast, pending status and human origin in the same amber hue, hue-only origin coding that disappears in greyscale, two different neutral palettes, and no radius, spacing or type scale. The owner rejected a first attempt at redesigning the foundations from scratch as generic, and asked for a comparison of established design systems and product design languages to build from.

Two surveys (21 Oct 2026) scored 30 implementation systems on ten criteria from the PRD and read 16 product design languages from their live CSS and documentation. The decisive constraint is the principal-side card: it renders inside a host iframe (Claude, ChatGPT, other MCP App hosts) that provides a small set of CSS variables and a font and forbids opaque backgrounds, custom fonts and more than two actions. Anything with a global stylesheet or a baked look fails there. Across hosts, the third-party vocabulary converges on: structure from the host, identity in one or two accents, status as background/border/text triplets with words, numbers tabular, both themes derived from few variables, alpha borders on borrowed surfaces. The only shipping precedent for marking who wrote what (iA Writer Authorship) sets human words plain and marks machine text with colour, the inverse of the prototypes' ochre-tinted human card.

The owner decided on 21 Oct 2026: human words plain, the machine carries the colour; React Aria Components as the base. The neutral question was delegated to the PM with a stated default.

## Decision

1. **Behaviour layer: React Aria Components (Adobe, Apache-2.0).** `packages/ui` wraps React Aria Components for every interactive element (buttons, toggle and radio groups for verdict and confidence, number and text fields, dialogs, menus, tabs, table, toast, date and time fields). Reasons: WCAG 2.2 criteria cited by name and a published screen-reader test matrix; zero CSS shipped, so the card is a clean guest; 30+ locales and RTL; released monthly. Rejected: Radix Themes (fastest complete kit but a global stylesheet, nine months without a release, and the "Linear look"), Mantine (widest coverage but a required global stylesheet and no accessibility statement), Base UI (comparable substrate, thinner accessibility evidence, no table), shadcn/ui (the 2024–26 default look), the corporate systems (Carbon, Primer, Fluent, Ant: each looks like its owner).
2. **The design layer is ours**, in three token tiers: primitives (OKLCH scales on a lightness ladder with a documented step contract: which step is text-safe on which background, in the manner of Radix Colors and USWDS grades), semantic roles (surface, surface-2, text, text-muted, border, border-strong, action, on-action, human, status triplets, focus), and component tokens. Primitives never leave `packages/ui`. Contrast is tested in CI: WCAG 2.2 ratios are **blocking** (text 4.5:1, large text and control boundaries 3:1, focus indicator 3:1); APCA is **reported, not blocking** (Lc 75 body, Lc 60 secondary as targets), so the ladder is a one-pass derivation and the hierarchy is not flattened by an advisory metric (PM's call after the builder check).
3. **Colour role model: human plain, machine coloured.** The participant's words (answer text, voice transcript, published profile paragraph) are the most typographically neutral element on any screen: text colour on surface, generous measure, no tint, no border colour. Agent drafts (the question as the agent wrote it), platform notes, status chrome and every interactive control carry the colour: one platform accent for all primary buttons, links, selected states and focus on all three surfaces. The attestation line (answered personally, confidence, timestamp, signature) sits under the answer in the mono role. This replaces the prototypes' and the current skill's "teal = agent, ochre = human, human card tinted ochre" with two roles only: `human` (plain text, no hue) and `accent` (platform and agent). There is no separate "participant action" hue: a second warm marker was considered and dropped because the one rule it would carry ("this is the person acting") is already stated by the button's label and the surface it sits on, and a second accent reintroduces the two-hue confusion the prototypes had (PM's call after the builder check). Colour is never the only signal: labels and the attestation text always accompany it.
4. **One neutral, tilted warm.** A single grey family for both surfaces, derived in OKLCH with a slight warm bias, close to the paper of the Claude host (`#FAF9F5`/`#F5F4ED` light, `#141413`/`#262624` dark as the reference points, not as copied values). Borders and dividers are alpha, so they sit on any host surface. Dark theme is derived from the same ladder, not hand-picked. Rejected: two neutrals (fragments the system without a felt difference); cool tilt (foreign inside the warm host, colder on a person's phone). This item is the PM's call under the owner's delegation and can be overruled at low cost before M2.
5. **Typography.** System font stack by default everywhere the budget or the host demands it: the request page and the answer form (2 s on 3G), the MCP App card (hosts forbid custom fonts), email. At most one web typeface, under about 60 KB, as a progressive enhancement on the dashboard and the participant home. No display serif. Numbers in tabular figures with their verb (held, cleared, returned, paid out); request ids and signatures in a 12–13 px mono role. One modular type scale on a 4 pt baseline; one spacing scale (4/8/12/16/24/32/48/64); one radius scale (4/8/12, pill); motion tokens with reduced motion as the default stylesheet.
6. **Guest subset for the MCP App card.** The card consumes the host's `styles.variables` (background, text, border, ring, font, radius) and adds only: the A2H accent on the primary button and one badge, and the status triplets. No own background, no own font, radius at most 8, at most two actions and five data points, a text fallback written first (it is also what terminals show). Stripe's Appearance API and the MCP Apps `HostContext` are the two external precedents. **How it is built and who owns it:** the card is a second build target of `packages/ui` (React + React Aria Components, zero global CSS, a host-variable adapter mapping MCP `styles.variables` onto our semantic roles), owned by Design; `apps/mcp` serves the built bundle as the `ui://` resource and Protocol dev touches nothing inside it. M1 verifies `request_human` with plain form-mode elicitation (text) in Claude Code and one web host; the rendered card is M5 (principal surface) scope and is not needed before the design-system work lands.
7. **Targets and states.** 44 × 44 px minimum for every control on the PWA including chips and toggles; 32 px with 8 px spacing on the dashboard. Status pills in sentence case, light background, dark text, always with words, at most four hues plus neutral for the six request states. Pending leaves the amber family.
8. **Distribution.** Components live in `packages/ui` as our own source wrapping React Aria Components (upstream dependency, not copy-in), styled with CSS modules and the semantic tokens; Storybook is the design source of truth until a Figma library exists (none ships with React Aria). Email templates in `packages/email` consume the semantic tokens inlined at build and never a web font.

## Consequences

- `.claude/skills/a2h-design` §2 (tokens) and §3 (colour convention) are rewritten from this ADR by the Design agent; §4 patterns are re-read so that the human answer card, the answer form transcript and the profile paragraph follow the plain-human rule, and "teal/ochre never inverted" becomes "human plain, machine coloured; no hue is ever applied to a human's words".
- `.claude/agents/design.md` and `web-dev.md` change their colour-convention line accordingly.
- Roughly a milestone of design-system work (tokens, 35–40 styled components, Storybook, contrast CI) precedes the first M2 screen; M1 has no rendered UI and is unaffected. **Sequencing (open, owner's decision):** the PM proposes running it as the first OpenSpec change of M2 (`m2-design-foundations`), not as a new milestone in PRD §10, validated at its Gate 2 on a deployed Storybook preview stage plus three screens recomposed from the new components (participant request email, answer form, principal answer card), with an early owner checkpoint on tokens and those three screens before the remaining components are styled. The alternative is to run it in parallel with M1 under an exception to one-change-at-a-time, which needs the Storybook preview stage in `infra/` during M0 step 4.
- The two prototypes remain the reference for product behaviour and copy; their colours and fonts are no longer normative.
- Open for the Design agent to settle in the design-foundations change, inside these rules: the exact OKLCH ladder values, the accent hue for the platform (teal remains the default candidate; it must read on Claude's warm paper and not collide with the host's own accent), the status hues, and the one optional web typeface.

## Alternatives rejected

- **Inherit a styled kit** (Radix Themes, Mantine, Chakra): faster to first screen, permanent "looks like them" tax, stripped build needed for the card.
- **shadcn-style copy-in of a React Aria base**: owning patched component source was not needed; upstream dependency keeps updates and the accessibility evidence intact.
- **Human tinted, machine plain** (the prototypes): no shipping precedent; tints the words that matter most; collides with warm host accents.
- **Two neutrals** and **a cool neutral**: see Decision 4.
- **A display serif for human words**: the only defensible job the prototypes' serif had; dropped because it cannot load in email or the card, costs 60–130 KB, and the plain-human rule gives the distinction without it.
