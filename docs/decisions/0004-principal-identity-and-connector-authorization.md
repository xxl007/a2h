# ADR 0004: Principal identity and connector authorization

- Status: proposed (takes effect when the product owner passes Gate 2 of `m1-hosted-connector`)
- Date: 2026-11-01
- Deciders: product owner (Galem L.), PM agent, Protocol-dev and Web-dev agents
- Scope: who a principal is to the platform, where sign-in and consent live, how an MCP client obtains and presents a token, how the MCP service verifies it, and how the web tier reaches the database to do so. Governs `apps/web` (authorization server), `apps/mcp` (resource server), `packages/db` (`principals`, `principal_policies`, Better Auth tables) and the stage configuration in `infra/`.
- Related: CLAUDE.md §Stack (Better Auth, magic link only) and §Engineering rules (every request carries an accountable principal); PRD §4 (request card), §11 (EU residency); `openspec/changes/m1-hosted-connector/` (proposal decisions 1–5, design D1–D8, D10; specs `platform/principal-identity`, `platform/connector-authorization`); ADR 0001 amendment 2 (Data API, WAF scope).

## Context

Until M1 the MCP endpoint had no notion of who was calling: one development principal was configured per stage, and any client that reached the URL acted as it. Hosted clients (claude.ai custom connectors, Claude Code, MCP Inspector) connect over the public internet to `https://mcp.<stage host>/mcp`, so the endpoint needs an accountable identity behind every call before any real participant can be addressed. The MCP specification (2026-07-28) makes the server an OAuth 2.1 resource server: it publishes protected-resource metadata naming an authorization server, challenges with `WWW-Authenticate`, and verifies bearer tokens; clients register through client-ID metadata documents (CIMD) or dynamic registration (DCR) and prove possession with PKCE. The specification's own reference authorization server is deprecated, so the platform has to run or rent one.

Constraints that shaped the choice: the product's sign-in library is Better Auth (CLAUDE.md), and participants will sign in with it in M2, so principals and participants should share one identity store; data stays in eu-west-3; the web Lambda runs outside the VPC and could not reach Aurora (ADR 0001 amendment 1, item 3); the MCP service is stateless Streamable HTTP and must verify tokens without a round trip per call; no PII or token may appear in a log (D10).

## Decision

1. **The authorization server is Better Auth in `apps/web`.** Issuer `https://<web host>/api/auth` per stage, plugins `jwt`, `mcp` (`@better-auth/mcp`), `cimd` (`metadataProfile: "mcp-2026-07-28"`) and `magicLink`. Sign-in, consent and the connected-clients screens are pages of the web app, owned by Web-dev. Running it inside `apps/mcp` would put HTML screens across the Protocol-dev boundary; an external identity provider adds a vendor, a bill and an EU-residency question for a function the chosen library already provides.
2. **A principal is a Better Auth user with a `principals` row.** The row (id = user id, `identity_mode`, `verified`) and its `principal_policies` row (the stage default copied at first consent: budget, caps, daily limits) are created in the transaction that records the consent. Policies are rows, not token claims, so a change applies on the next call and the worker reads them without a token. The id is opaque and is the only identity that reaches logs.
3. **Sign-in is a magic link to an allow-listed address, nothing else.** The allow-list is an SSM SecureString per environment, read at cold start and refreshed every five minutes; the sign-in action answers in constant time whether or not the address is known. On non-production stages the link is written to an S3 mail sink readable only through the deploy role; only production can send email.
4. **Token format.** Access tokens are JWTs signed with EdDSA (Ed25519) keys kept in the `jwks` table and published at `<issuer>/jwks`. Claims: `iss` the stage issuer, `sub` the principal id, `aud` exactly the stage's MCP URL as named by the `resource` parameter, `scope` from `a2h` (the tools) and `offline_access` (refresh), `exp` at most one hour after issue. Refresh tokens rotate on every use with a reuse interval of zero: a replayed refresh token is refused and its family revoked. **Access tokens are not individually revocable**; sign-out and "disconnect" act on refresh tokens and consents, and the one-hour lifetime bounds the exposure. This is the trade-off that lets the resource server verify locally.
5. **The MCP service is a resource server that verifies locally.** It serves `/.well-known/oauth-protected-resource<mcp path>` per stage (`resource`, `authorization_servers`, `scopes_supported: ["a2h"]`), bypasses the gate only for health, the metadata and, on non-production stages with `PING_OPEN`, the `ping` tool, and verifies every other request with the SDK's `requireBearerAuth` and a `jose` remote JWKS (cooldown 60 s, cache 10 min): `iss`, `aud` with no trailing-slash or prefix leniency, `exp`, `scope`. Any failure is 401 with the challenge; a missing scope is 403. The token's subject is the principal of the call: tool dependencies are built per request, and an approval state minted for one principal fails for another. Tokens are never forwarded to the worker or to any outbound call.
6. **Clients.** CIMD and DCR are both enabled; dynamic clients are public (`none` authentication, native application type so loopback redirects of CLI clients pass), PKCE S256 is required, the RFC 9207 `iss` parameter is emitted, and registrations unused for 30 days are pruned by the worker. Pre-registered clients with a secret come from stage configuration for hosts that can use neither. No OpenID Connect discovery in M1: the server is OAuth-only, and adding `openid` would first need a plain-words line on the consent screen.
7. **The web tier reaches Aurora through the RDS Data API** with the Lambda's role and the stage's secret, scoped to the stage's schema by the database login (previews as `pr_<n>`, dev as the master user). No password in the function's environment, no VPC attachment, no NAT gateway. The same path CI uses for migrations; the production cluster has the Data API enabled so its first deploy can migrate the same way. Recorded for the stack in ADR 0001 amendment 2.

## Consequences

- Every tool call carries a principal id from a verified token; `find_humans`, `request_human` and `check_requests` require scope `a2h`; `check_requests` from another principal reports `not_found`.
- A compromised access token is valid for up to one hour against one stage's MCP URL only. If individual revocation ever becomes a requirement, the resource server gains an introspection or denylist round trip, and this ADR is amended.
- Previews are separate issuers and audiences; a preview token is refused on dev and the reverse (spec scenario "Preview tokens stay on the preview").
- Participants (M2) reuse the same Better Auth instance: same `user` table, a different role and screens. Identity verification (Stripe Identity, M4) attaches to the user, not to the token.
- Data API latency (tens of milliseconds per statement) is paid only on sign-in, consent and token paths. If it ever bounds a page budget, the NAT-instance alternative is an `infra/` change (ADR 0001, decision 2 pattern).
- The allow-list is the product's gate until self-service principal onboarding exists (M5): a stage can only be used by addresses the owner has listed.
- Owner actions that remain manual: the allow-list parameter per environment (runbook §15) and pre-registered clients in stage configuration.

## Alternatives rejected

- **Authorization server inside `apps/mcp`** (SDK reference server): deprecated upstream, HTML screens in the protocol service, a second identity store for participants later.
- **External identity provider (WorkOS, Auth0, Cognito)**: a vendor and a bill for a function Better Auth provides; EU residency and the single-account posture would need review; participants would still need the product's own screens.
- **Opaque tokens with introspection per call**: revocable at once, but a round trip from the stateless MCP service on every call and a dependency of the protocol path on the web tier's availability.
- **Policies as token claims**: a policy change would wait for the token to expire; the worker needs the policy without a token.
- **Lambda in the VPC behind a NAT instance**: a monthly cost and a single point of failure for the web tier, for two tables of sign-in state.
- **Password or social login for principals**: CLAUDE.md fixes magic link only; LinkedIn and X are read-only imports for participants, never a login requirement.
