# Design: m1-protocol-connector

## Context

See proposal.md for motivation. What exists after M0: a stateless MCP server (`@modelcontextprotocol/server` 2.4.0 behind `createMcpHandler`, one server instance per HTTP request, no sessions) on ECS Fargate behind a public HTTP ALB; a pg-boss worker with database credentials from Secrets Manager and the RDS CA bundle baked into its image; Aurora Serverless v2 with the Data API enabled, one schema per preview owned by a per-preview login, `public` for `dev`; `packages/protocol` and `packages/db` empty. Constraints that shape this design: the server must stay stateless across instances (spec `mcp-transport`), there is no authorization yet (so one development principal per stage), no NAT gateway (services reach only the database and AWS endpoints), the preview login may create objects only inside schemas it owns, and the mcp and worker images bundle workspace packages by copying built output.

## Goals / Non-Goals

**Goals:**
- Approval without server-side session state: a stateless server must still make "accept creates exactly what was approved" hold.
- One database access path shared by mcp and worker, with migrations applied before services roll.
- Simulated answers indistinguishable in shape from real ones, impossible to mistake for real ones in content.
- Every OPEN item of the protocol skill stays a parameter.

**Non-Goals:**
- Authorization, rate limiting by caller identity, TLS: `m1-hosted-connector`.
- Any money movement or Stripe object.
- A participant-side surface or email.

## Decisions

### D1. Approval rides the 2026-07-28 multi-round-trip flow, with integrity-protected state
`request_human` validates the manifest, then returns an `input_required` result with one embedded form-mode elicitation (`requestedSchema`: one string property `question` whose `default` is the validated text; the message carries gross bid, format, expiry, data terms and "Send · hold €N") and a `requestState`. The client retries the same call with `inputResponses`; the handler re-validates the full manifest with the approved text, creates the request in one transaction, and returns the result. `requestState` is an opaque token minted by the server: HMAC-SHA256 over `{principal_id, manifest_hash, nonce, issued_at}` with a per-stage secret, verified through the SDK's `requestState.verify` hook; a token that fails verification, is older than 15 minutes, or whose `manifest_hash` does not match the retried arguments is refused with `conflict`. Nothing about the pending approval is stored.
- Why: the spec and the SDK make elicitation a multi-round-trip result on this revision; push-style `elicitInput` needs a session and fails on the stateless path. HMAC state keeps the server stateless and makes the echoed state tamper-evident, as the MRTR spec requires.
- Alternatives: a `pending_approvals` table keyed by nonce (works, adds a write per approval and a cleanup job); sticky sessions (the ALB cannot pin MCP clients without cookies); a session-ful single task per stage (fallback only, see Risks).
- Fallback if task 1 shows Claude Code on the 2025 path: run the mcp service with `desiredCount: 1` and SDK sessions for M1 only; the stateless design is restored when the client negotiates 2026-07-28. Recorded here so that no code is written for it unless the spike fails.

### D2. Postgres access: one adapter per app, Drizzle for queries, plain SQL migrations applied from CI through the Data API
`packages/db` holds the Drizzle schema and the SQL migration files generated by `drizzle-kit`. The mcp service gets the same database environment the worker has (`DB_HOST`…`DB_PASSWORD`, `DB_CA_BUNDLE`), through an adapter `apps/mcp/infra/env.ts` mirroring the worker's. Queries go through Drizzle over `pg`. Migrations are applied by `.github/scripts/db-migrate.sh <stage>` before `sst deploy`, using the Data API like `pr-schema.sh`, inside one transaction per migration file, tracking applied files in `<schema>.schema_migrations`; for previews the transaction starts with `SET ROLE pr_<n>` so the login owns every object it creates. Locally, `drizzle-kit migrate` against the Docker Postgres already used by the CI script tests.
- Why: the runner is outside the VPC, and the Data API path is already proven and permitted for the deploy roles; applying migrations before the services roll keeps the services simple and makes a failed migration visible in the run log, before any task restarts.
- Alternatives: migrate at worker start under an advisory lock (couples readiness of mcp to the worker's boot order and hides failures in task logs); Drizzle's Data API driver from the runner (a second driver to maintain for one purpose).

### D3. pg-boss gets its own schema
`dev` and `prod`: `pgboss`. Previews: `pr_<n>_jobs`, created and owned like `pr_<n>` by `pr-schema.sh` (which becomes the one script that creates everything a preview login owns). The worker reads `DB_JOBS_SCHEMA`; `createSchema` stays false. Resolves M0 note D1 before the first Drizzle table lands in `public`.

### D4. Signing: Ed25519 through WebCrypto, keys platform-held per stage
`packages/protocol` exports `canonicalAnswerPayload`, `signAnswer(payload, privateKey)` and `verifyAnswer(envelope, publicKey)` on `globalThis.crypto.subtle` (Ed25519 is available in Node 22 and in browsers), taking key material as arguments, so the package stays free of Node-only modules. Private keys live in Secrets Manager (`a2h/<stage>/signing`, created by `pr-schema.sh` for previews and once by the runbook for `dev`), the worker's simulator reads them at start; public keys with `key_id`, `created_at`, `status` (`active` | `rotated` | `revoked`) live in a `signing_keys` table so verification works after rotation. One platform key per stage in this change; one key per participant arrives with real participants (M2/M3) using the same table.
- Alternative: `@noble/ed25519` (one more dependency for something the runtime provides).

### D5. Tool shapes, JSON Schema and structured results
Zod 4 schemas in `packages/protocol` with `z.toJSONSchema` for the export; each tool registers `inputSchema` and `outputSchema` from the export and returns both `structuredContent` and a text rendering. The package gets `tsconfig.build.json` emitting ESM to `dist/` with an `exports` map; the mcp and worker Dockerfiles copy the built package. Node does not type-strip `.ts` under `node_modules`, so this is the end of the M0 exemption.

### D6. Validation pipeline as pure functions over loaded facts
`packages/protocol` exports `validateManifest(manifest, facts, policy)` returning the first `ProtocolError` or the deferred delivery time; `facts` (participant rules, today's interruption count, principal budget use, rate-limit count) are loaded by the caller (mcp at approval, worker at fan-out) so the function is testable without a database. Forbidden-content detection in this change is a deterministic rule set (patterns and structural checks such as leading questions with an embedded claim, requests naming a third person's personal attributes, imperative work verbs with deliverables) with a fixture per class; the method remains OPEN in the skill and a model-based classifier would be an M3 proposal. The one rule does not depend on the method: the rejection point and the categories are fixed.

### D7. Development principal and policy per stage
No authorization exists yet, so each stage has one principal: `principal_id` `dev-principal-<stage>`, identity mode "verified organisation (development)", monthly budget, per-request cap, ask-first thresholds and daily rate limit from `infra/config.ts`, surfaced as environment. Budget use is counted from requests in the current month. The `authorisation` intent is refused for this principal (not real-name verified), which also exercises that rule.

### D8. Simulator as worker queues
Queues: `deliver` (re-validate, then enqueue a `simulate` job with the persona's delay; a real delivery job takes this place in M3), `simulate` (apply the persona: accept, answer with a body generated per intent, decline, or do nothing), `expire` (scheduled every minute: `sent`/`accepted` past expiry → `expired`). Personas and the twelve profiles are a seed file in `packages/db/seed/` applied idempotently by `db-migrate.sh` on non-production stages (upsert by handle). Simulated answers are signed with the stage key and stored like real ones; `simulated` is a column on participants, surfaced in `check_requests`.

### D9. Logging
Every log line carries `request_id`, `principal_id`, `participant_id`, state and code; never question or answer text. Tool errors carry the category `detail` only. Tests assert the absence of text fields in captured log lines for the blocked and rejected paths.

## Risks / Trade-offs

- [Claude Code negotiates the 2025 revision with this server] → task 1 proves the modern path with a throwaway `approve_test` tool on `dev` before anything else; if it fails, D1's fallback is applied as a one-line infra change and the stateless design returns later.
- [HMAC state secret leaks] → the token can only let an attacker approve a manifest they already hold with its exact hash, under the development principal; rotation is one secret update; the secret never reaches the client.
- [Edited question drifts from the validated one] → full re-validation on retry (D1), with the approved text; the manifest hash binds every other field.
- [Data API `SET ROLE` semantics] → verified by the CI script test against Postgres 17 in Docker before the workflow changes; if `SET ROLE` is not honoured across statements in a Data API transaction, fall back to `ALTER … OWNER TO pr_<n>` after each migration.
- [Twelve simulated profiles read as a real marketplace] → `sim-` handles, "(simulated)" labels and `simulated: true` everywhere; the simulator is absent on `prod`.
- [Protocol build step breaks the Docker builds] → the build is run in CI's `check` job and the preview deploy exercises both images on the PR itself.

## Migration Plan

1. `pr-schema.sh` learns the second schema and the signing secret; `db-migrate.sh` is added; both are covered by the CI script tests. Existing previews are unaffected until their next deploy.
2. Deploy workflows: `db-migrate.sh` runs after credentials, before `sst deploy`; on previews after `pr-schema.sh create`.
3. `dev`: the owner creates `a2h/dev/signing` once (runbook step); the first deploy migrates `public`, creates `pgboss`, seeds the simulated set.
4. Rollback: images roll back through SST; migrations are forward-only and additive in this change (no destructive statement), so an older image runs against the new schema.

## Open Questions

- Which twelve topics the simulated profiles cover (owner decision 3 at Gate 1; defaults proposed in tasks.md and changeable in the seed file without a spec change).
- Whether `eta` should be the participant's latency promise or the persona's delay on simulated participants (default: the latency promise, since that is what a real participant publishes).
